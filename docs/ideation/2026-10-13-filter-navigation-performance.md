# 2026-10-13 缓存筛选、连续导航与下载调度

## 代码分析与本轮方向

检查基于 `main` 的 `12032e0`。项目已有源配置与诊断、搜索分页、下载计划和恢复；
本轮继续使用 Python、cmd.Cmd、Rich，不引入新的运行依赖。

| 维度 | 代码中的问题 | 实现与边界 |
| --- | --- | --- |
| 操作性 | 多源结果只能逐页浏览，无法按名称、作者或来源缩小范围 | `f` 在最近一次完整缓存上筛选，分词全部匹配、忽略大小写；保留原序号 |
| 操作性 | 页码需要手动记忆，空参数固定回第一页 | `p next/prev`，`ch <分组> next/prev`；空参数重显当前页；各分组独立记忆 |
| 状态反馈 | 缺少筛选状态、无匹配与页码边界反馈 | 条件/匹配数/页码面板、清除筛选提示、边界检查；`status` 显示当前位置 |
| 界面 | 搜索表格边框较重，40 列帮助说明被挤成省略号 | 简化横向表头；窄屏帮助改为两列折行；外部内容继续按字面渲染 |
| 性能 | `_run_image_downloads` 一次性为全部图片创建 Future | 以有效线程数的两倍为窗口滚动提交，完成即补位，额外调度状态为 O(线程数) |
| 资源管理 | `_request_image` 抛出 HTTP 状态异常时响应未传到外层清理 | 在抛出异常前关闭响应，允许连接资源及时释放 |
| 可诊断性 | 并发失败明细按完成顺序排列 | 最终按图片原序号排序，便于定位文件 |

筛选不会删除原始搜索结果、改变当前漫画或改变下载命令含义。新搜索清除筛选并回到第一页；
重新展示新漫画详情会重置章节页码。翻页与筛选不发网络请求，不抓取网站的下一页。
图片队列仍使用原有线程独立 HTTP Session、限速、浏览器锁、文件校验与持久化机制。
图片 URL 列表和失败结果仍随章节规模增长，本轮减少的是 Future/待执行任务的调度占用。

  另验证慢首图不阻塞其他线程补位、主线程中断、工作线程取消、HTTP 错误关闭响应。
- 终端检查：实际渲染 40/80/120 列筛选结果与空结果，40 列帮助无省略号；
  README 中的 SVG 来自 Rich 的实际输出，使用明确标注的演示数据。
- 检查命令：`uv run pytest -o addopts= -q`、本轮 Python 文件的 `ruff check` / `ruff format --check`、
  `uv run pyright --pythonpath .venv\Scripts\python.exe`、`git diff --check`。

本轮全量测试结果为 **322 passed**（新增 17 项）；类型检查零错误、零警告。
另外使用独立 Python 进程通过帮助、40 列交互命令、管道 EOF 和来源概览四组冒烟检查，
均正常退出；这些只读流程没有创建下载任务记录。

本机离线基准使用 10,000 个图片 URL、5 个线程，将下载函数替换为空操作，
在 URL 列表构造后启用 `tracemalloc`，比较基线与本轮 `_run_image_downloads`。
基线峰值约 **16.53 MiB**，滚动队列约 **0.06 MiB**；两次运行均得到相近的峰值。
这只衡量 Python 调度分配，不包括浏览器、真实图片内容、网络速度或进程总内存。
空任务的调度耗时有小幅增加，因此不将其解释为下载提速。

这些验证覆盖本地逻辑，不证明外部漫画站点当前可用，也不替代各浏览器模式的在线端到端验证。
