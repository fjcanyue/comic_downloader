# 已完成计划归档与恢复

本轮从 `93b6897` 开始，测试基线为 416 项。任务分页、筛选和摘要缓存已经解决了
长列表展示与重复解析问题，但已完成计划一直参与主列表扫描。加入显式归档，可以
将这些历史记录移到独立列表，继续保留章节执行结果和恢复入口。

## 操作设计

统一使用 `archive` 命令：无参数或 `list [页码]` 查看归档，`<任务ID>` 归档一个已完成
计划，`show <任务ID> [页码]` 查看章节，`restore <任务ID>` 恢复到主列表。
交互命令与直接子命令共享参数解析器；直接命令的语法错误在 Shell 初始化前返回退出码 2。

归档列表每页 20 项、章节每页 30 话，沿用当前任务表格的布局、窄屏折行和稳定 ID。
归档界面提供对应的查看、恢复、分页命令，不引导用户直接重试归档计划。
纯数字十六进制前缀仍按任务 ID 处理；列表翻页使用明确的 `archive list 2`。
归档操作不切换当前漫画，也不修改搜索或任务浏览状态。

## 存储与并发

计划从 `.comic_downloader/jobs/<ID>.json` 移至其 `archive/` 子目录。原始 JSON 字节、
ID、创建时间、更新时间与章节结果保持不变，沿用版本 1 格式。恢复执行反向移动。
排序继续使用原更新时间，因此恢复后的计划不一定出现在列表首位。

两种操作使用主任务目录下相同的每任务 OS 锁，与下载执行互斥；取得锁后重新读取
完整 ID 的记录，以发现等待期间的状态变化。归档要求计划状态为 `completed` 且没有
未完成章节。目标有同 ID 记录时拒绝覆盖；同一输出文件系统内执行重命名，失败时保留
源记录。损坏记录无法移动，归档列表仍隔离报告错误并显示其他有效计划。

主列表的扫描不递归进入归档目录，归档列表复用既有摘要缓存与文件元数据刷新机制。
这减少主列表参与扫描的记录数，没有引入额外索引文件或宣称未经测量的速度提升。

图片、ZIP 和独立章节恢复记录 `tasks.json` 不参与移动。归档不是文件清理或内容完整性
校验，也不会自动删除任何记录。恢复后的已完成计划保持已完成状态；需要重新下载时
仍应重新创建计划。默认不引入批量归档、保留期限或永久删除操作。

## 验证

新增 38 项测试，覆盖：

- 归档和跨实例恢复后的原始字节、ID、时间、漫画文件、独立章节记录保留。
- 未完成状态、损坏完成记录、前缀歧义、目标冲突、移动失败及加锁后的状态变化。
- 独立 Python 子进程持锁冲突，归档与恢复均无法绕过下载锁。
- 真实 CLI 的归档、列表、详情、恢复往返流程。
- 23 个归档计划的分页、35 话详情分页、损坏记录隔离、失败退出码和交互状态保留。
- 40、80、120 列终端的字面文本与归档操作提示。

全量测试 454 项通过。修改的 8 个 Python 文件通过 Ruff 检查及格式检查；
项目 Pyright 检查为 0 错误、0 警告。`docs/job-archive.svg` 来自真实 Rich 渲染的
演示数据，另检查了 40、80、120 列的文本输出。验证全部使用本地临时记录，
没有访问漫画站点，也没有移动用户真实下载记录。
